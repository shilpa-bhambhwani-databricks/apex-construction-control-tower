# Construction Control Tower

**Industry:** commercial construction (general contractor).
**Customer problem:** margin fade and schedule slip on large projects are discovered too late, because the warning signs sit in separate systems — RFIs and submittals in the project management system, cost in the ERP, float in the scheduling tool, change orders in a change-management system, near-misses in the safety system, and the rules about who pays in contract PDFs.

The Control Tower is a working prototype on Databricks that brings those signals together for a fictional contractor, "Apex Construction":

- **Portfolio Risk Radar** — one governed 0–100 risk score per project from six signals, with plain-English Q&A and one-click follow-ups.
- **Project Resolve** — an agent that checks a change order or RFI against the contract, subcontract, specs, daily logs and historical unit rates, and returns a cited recommendation for a person to approve.
- **Jobsite Intelligence** — a superintendent's "ready to work?" view of the next two weeks, with safety-standards Q&A.
- **Margin Watch** — bid vs. projected margin by project for the office of the CFO, through a Genie Agent.

All data is synthetic. Projects, costs, schedules, change orders, safety observations, contracts and specs are generated by the scripts in `data_gen/`. No customer data, names or documents are in this repository.

## The journey, end to end

```text
 data_gen/*.py  ──►  Unity Catalog volume (raw parquet extracts + PDF documents)
                          │
        ┌─────────────────┴──────────────────┐
        ▼                                    ▼
 1. LAKEFLOW pipeline                 ai_parse_document  ──►  chunks  ──►  AI Search index
    bronze (9 streaming tables)              │                                │
    silver (2 quality-checked MVs)           │                                │
        │                                    │                                │
        ▼                                    ▼                                ▼
 2. UNITY CATALOG ── one schema: tables, volumes, functions, metric views; one row filter on every layer
        │                                                                     │
        ├──►  metric view  project_risk_mv  (source = pipeline silver tables) │
        │         │                                                           │
        │         ├──►  5. GENIE AGENT "Portfolio Risk"   (runs as the asker; row filter applies)
        │         │                                                           │
        │         └──►  6. DATABRICKS APP  Risk Radar page                    │
        │                                                                     │
        └──►  4. GEN AI agents (Project Resolve, Jobsite Intelligence)  ◄─────┘
                  tools = UC functions + AI Search; every run traced in MLflow
                      │
                      ▼
 3. LAKEBASE (Postgres) ── follow-ups, notifications, human decisions (each decision stores the MLflow trace id)
                      ▲
                      └── written and read by the app on every action
```

How the stages depend on each other — this is one journey, not six demos:

- The **risk score** the app shows and Genie answers from is a Unity Catalog **metric view** whose sources are the **Lakeflow pipeline's silver tables**. Unity Catalog lineage records the chain `bronze → silver → project_risk_mv` (see `evidence/02_unity_catalog.md`).
- The **same row filter** (`ct_row_scope`) is attached to the pipeline's bronze and silver tables and to every other project-scoped table, so one identity sees the same projects in SQL, in the app, in Genie and through the agents: 40 for operations leadership, 11 for a Northeast project manager, 1 for a superintendent.
- The **agents** call governed **Unity Catalog functions** and an AI Search index built from documents parsed with `ai_parse_document`; they never query outside the catalog.
- A person's decision on an agent recommendation is written to **Lakebase** together with the **MLflow trace id** of the agent run it was based on, so the operational record points back to the AI evidence.
- The **app** declares each stage as a resource: SQL warehouse, Genie Agent, Lakebase database, model serving endpoint.

- 9 feeds, 21,352 rows ingested by the pipeline; a second update ingested 0 new bronze rows (incremental) and recomputed silver.
- 10 of 10 data-quality expectations passing; 0 rows dropped.
- Risk metric view returns identical results before and after its source was moved from script-loaded tables to the pipeline's silver tables.
- Row-level security: 40 / 11 / 1 projects visible to three identities at bronze, silver, metric view and Genie.
- Change-order agent: 12 traced steps in 22.6 seconds (1 change-order lookup, 5 document retrievals, 2 unit-cost benchmark lookups, 3 model rounds), answer cited to document, page and section.
- Genie: 7 of 7 questions completed in 18–28 seconds.
- Lakebase: 3 follow-ups, 6 notifications, 1 decision linked to its MLflow trace.

## Run it yourself

Prerequisites: a Databricks workspace with Unity Catalog, serverless SQL and pipelines, Lakebase, Databricks Apps and AI Search; the Databricks CLI with a configured profile; Python 3.11+; Node 20+.

```bash
export DATABRICKS_PROFILE=<your profile>         # scripts default to a profile named apex-construction
export CATALOG=<catalog you own> SCHEMA=construction_control_tower WAREHOUSE_ID=<sql warehouse id>

# 1. Generate synthetic data locally, then upload it to UC volumes (the upload is a manual CLI step)
python data_gen/generate.py && python data_gen/documents.py && python data_gen/finance.py && python data_gen/finance_docs.py && python data_gen/ehs_standards.py
V=dbfs:/Volumes/$CATALOG/$SCHEMA
databricks fs cp -r data_gen/out           $V/raw/v1            -p $DATABRICKS_PROFILE   # core feeds (pipeline source)
databricks fs cp -r data_gen/out_docs      $V/raw/v2            -p $DATABRICKS_PROFILE   # unit costs, CO lines, historical RFIs
databricks fs cp -r data_gen/out_jobsite   $V/raw/v3            -p $DATABRICKS_PROFILE   # jobsite tables
databricks fs cp -r data_gen/out_docs/pdf  $V/documents/atlas   -p $DATABRICKS_PROFILE   # contracts, specs, logs
databricks fs cp -r data_gen/out_docs/ehs  $V/documents/ehs     -p $DATABRICKS_PROFILE   # safety standards
databricks fs cp -r data_gen/out_finance/pdf $V/finance_documents -p $DATABRICKS_PROFILE

# 2. Lakeflow pipeline: bronze + silver
cd lakeflow && databricks bundle deploy -p $DATABRICKS_PROFILE && databricks bundle run control_tower_ingest -p $DATABRICKS_PROFILE && cd ..

# 3. Governed tables, row filters, metric views, functions, document parsing
python scripts/setup_identities.py
for f in scripts/0*.sql scripts/1*.sql; do python scripts/run_sql.py "$f"; done

# 4. Genie Agents, then the app
python scripts/create_genie.py && python scripts/create_genie_jobsite.py && python scripts/create_genie_finance.py
python scripts/deploy_app.py && scripts/deploy.sh

# 5. Prove it ran
python scripts/verify_personas.py
python scripts/capture_evidence.py
```

The SQL scripts and pipeline use the catalog and schema of the workspace this was built in (`bhambs.construction_control_tower`); change those names to your own. `scripts/04_access.sql` contains placeholders for the presenter's user name and the two service-principal application ids that `setup_identities.py` prints.

## Honest notes

- **What the pipeline feeds today.** The Lakeflow pipeline ingests all nine raw feeds to bronze. Its silver tables feed the risk metric view — the path behind the Risk Radar page and the Portfolio Risk Genie Agent. The detail tables the app reads for drill-downs (RFIs, change orders, job cost, jobsite tables) are still the script-loaded copies (`scripts/01`, `05`, `10`, `14`), because a few of them carry post-load edits that keep the demo storyline consistent. Moving those onto silver tables is the natural next step.
- **Weekly risk signals are generated, not derived in the pipeline.** The six sub-scores per project per week are computed by `data_gen/generate.py` from the raw rows and land as a feed. The pipeline validates and de-duplicates them; it does not recompute them.
- **Lakebase is the app's operational store**, written and read by the app. It does not serve a synced copy of lakehouse tables.
- **The first pipeline updates failed** and are left in the update history: a streaming `read_files` source needs a directory or glob, not a single file path. The fix was glob patterns (`rfis*.parquet`).
- **Two setup steps were done by hand and are not scripted here:** uploading the generated files to the volumes (commands shown above), and creating the AI Search endpoint and the delta-sync index `doc_chunks_index` over `doc_chunks` (done in the workspace UI; embedding model `databricks-gte-large-en`). The index status and a live retrieval query are in `evidence/04_gen_ai.md`.
- **Simulated identities** are service principals standing in for a regional project manager and a superintendent. In production each user signs in with SSO.
- **Agent traces** come from real runs of the deployed app between 2026-11-09 and 2026-11-18. Older traces keep only request and response previews; newer ones keep full span data.
- Vendor names such as Procore, SAP and Primavera P6 describe the *shape* of the synthetic feeds. Nothing was extracted from those systems.
